# bridgingassets — frozen reference content for `POST /api/bridging/exhibit`

JSON has no comment syntax, so provenance for the two embedded fixtures lives
here instead of in a file header. Both files are embedded verbatim via
`go:embed` from `kit/kitd/bridging.go` and are **FROZEN reference content**:
the `kit` Go module cannot import the platform repo's `testdata/golden/` (it is
a separate module, pinned against published `shn-gateway`/`shn-sdk` releases —
see `kit/go.mod`), so these bytes are hand-regenerated copies, not a live
read of the platform goldens. If the source goldens below change shape, these
two files go stale silently — there is no CI tie between them — and must be
regenerated by hand using the recipe below.

## carry-input-2.2.json

**Source:** `testdata/golden/2.2/questionnaireresponse-autofill.json`
(repo root), the real DTR 2.2 autofill `QuestionnaireResponse` golden used by
`test/conformance/dtr_transform_live_test.go`.

**Why it's not the golden verbatim:** no real golden in the repo carries an
`item.answer.value.extension:itemWeight` element (`gateway/engine/transform_dtr.go`'s
`dtrItemWeightExt` doc — SHN's own `FillQuestionnaire` never stamps one; only
a *foreign* 2.2 payload might). The carry exhibit exists specifically to
demonstrate that content, so one is injected at authoring time: the
`conservative-therapy-weeks` item's first answer gains a `_valueInteger`
sibling object holding

```json
{"url": "http://hl7.org/fhir/StructureDefinition/itemWeight", "valueDecimal": 0.5}
```

**Why `_valueInteger` and not the answer itself:** `itemWeight` is a core FHIR
extension and its `StructureDefinition.context` is `Coding`,
`Questionnaire.item.answerOption`, `QuestionnaireResponse.item.answer.value` —
*not* the answer BackboneElement. A profile cannot widen an extension's context
and the validator enforces the context, so the `item.answer.extension:itemWeight`
slice DTR 2.2.0's own differential declares is unsatisfiable on the wire
(an upstream IG defect), and the engine reads the SD. This answer is
`valueInteger`, a primitive — a JSON scalar cannot carry children, so FHIR puts
its extensions on the sibling `_valueInteger` object. A Coding-valued answer
would carry them on the value object itself.

**Why the byte layout looks "canonicalized" (alphabetized keys, not the
golden's original field order):** `POST /demo/transform`'s handler
(`gateway/app/demo_endpoint.go`) round-trips every payload through
`encoding/json`'s `map[string]any` decode/re-encode (`applyChain`'s step
functions), which always emits object keys in sorted order. The kitd handler
proves the carry-then-restore round trip is byte-identical
(`bytes.Equal(restored, embeddedInput)`) — for that proof to hold, the
*embedded input itself* must already be in that same canonical form,
otherwise the very first step (a marshal-driven relocation) would itself
introduce a byte diff unrelated to the carry mechanism. So this file is the
golden + injected extension, then re-marshaled once through
`encoding/json.Marshal` — the exact process `pa.dtr 2.2->2.1` would perform
on it anyway — not a hand-formatted document.

**Exercises at runtime:** `pa.dtr 2.2->2.1` (down) carries the itemWeight
extension into an `shn-carried-content` wrapper
(`dtrCarryItemWeight`/`shnsdk.CarryElement`), replacing it **in place** inside
`_valueInteger.extension` — the LossReport's `carried` entry names
`QuestionnaireResponse.item.answer.value.extension:itemWeight`. Then
`pa.dtr 2.1->2.2` (up) restores it in the same array
(`dtrRestoreItemWeight`/`shnsdk.RestoreCarried`), and the handler checks the
restored bytes against this file. The wrapper's position is what tells restore
which JSON encoding of `answer.value` the element came from.

## refusal-input-2.1.json

**Source:** `testdata/golden/2.1/questionnaireresponse-autofill.json` (repo
root) — the real DTR 2.1 autofill golden, which already carries exactly one
`Coverage`-referencing `qr-context` extension (the honest, single-coverage
shape every real SHN-produced QR has).

**The crafted mutation:** a *second* `Coverage`-referencing `qr-context`
extension is appended:

```json
{
  "url": "http://hl7.org/fhir/us/davinci-dtr/StructureDefinition/qr-context",
  "valueReference": {"reference": "Coverage/MBR-SECONDARY"}
}
```

This is the exact shape `gateway/engine/transform_dtr.go`'s
`dtrRelocateCoverageUp` refuses: going `pa.dtr 2.1->2.2` (up), DTR 2.2's
`qr-coverage` extension must relocate from a *single* unambiguous
`Coverage`-referencing `qr-context` entry (`dtrQRContextExt` =
`http://hl7.org/fhir/us/davinci-dtr/StructureDefinition/qr-context`, matched
by `valueReference.reference` having prefix `"Coverage/"`); two or more such
entries is ambiguous foreign content with no honest single source, so the
transform returns a typed `*engine.SemanticChangeError` (`Direction: "up"`,
naming `QuestionnaireResponse.extension:qr-coverage (ambiguous: 2
Coverage-referencing qr-context entries, multi-coverage source)`) —
`POST /demo/transform` maps that to its 422 wire shape
(`{"refusal": "...", "semanticChange": true}`), which this exhibit surfaces
verbatim.

Same canonicalization note as the carry fixture applies (the golden +
mutation, re-marshaled once through `encoding/json.Marshal`) — though for
this fixture it matters only for byte-stability of the checked-in file, not
for a round-trip proof (a refused transform never produces output to compare
against).

## Regeneration recipe

If `testdata/golden/2.1|2.2/questionnaireresponse-autofill.json` changes
shape, regenerate both files with a throwaway `_test.go` inside
`gateway/engine/` (deleted after use — never committed) that:

1. Reads the golden(s) via `os.ReadFile`.
2. Applies the same mutation described above (`json.Unmarshal` to
   `map[string]any`, append the extension, `json.Marshal` back).
3. For the carry fixture: calls `engine.RunTransformChain("pa.dtr", "2.2",
   "2.1", …)` then `RunTransformChain("pa.dtr", "2.1", "2.2", …)` on the
   result and asserts `bytes.Equal` against the mutated-and-marshaled input —
   if that assertion doesn't hold, the file you're about to check in would
   fail `bridging_test.go`'s round-trip test.
4. For the refusal fixture: calls `engine.RunTransformChain("pa.dtr", "2.1",
   "2.2", …)` and asserts it returns a `*engine.SemanticChangeError`.
5. Writes the marshaled bytes (step 2's output, not the transform output) to
   `kit/kitd/bridgingassets/{carry-input-2.2,refusal-input-2.1}.json`.

This was run once at authoring time (2026-08-14) against the
goldens as they stood then; `kit/kitd/bridging_test.go`'s embedded-asset
sanity tests (QR-parses, itemWeight-present, ≥2-Coverage-qr-context-present)
are the CI-visible tripwire if these two files and the live transform ever
drift apart.
